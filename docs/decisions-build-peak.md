# 决策记录：构建瞬间峰值优化（2026-11-18 起）

> 背景：v2.20.0 把稳态内存压到 ~61MB 存活 / RSS ~4MB，但构建瞬间峰值 ~500MB
> （略高于 v2.19.0 基线 429MB）。用户要求研究减小峰值。沿用 grill 流程，
> 强度=细问（沿用上轮），行为零变化与「只替换目录生效」两条硬约束继承。

## 实测事实（2026-11-18，SDK 2.23.0 隔离环境，真实素材 + 36MB 同步库）

分阶段 RSS/commit 测量（工作区 _peakphase.py）：

| 阶段 | RSS | 说明 |
|---|---:|---|
| 构建开始 | 43 MB | Python 基线 |
| 整句表压实入口 | 421 MB | 两张 dict 已建好（~300MB）+ 常驻歌词 23MB + meta |
| 整句表压实出口 | 437 MB | 整句 dict 释放，紧凑层 12MB |
| 子串表压实出口 | **500 MB（峰值）** | 子串 dict 254MB 未释放 + 压实临时 ~60MB |
| trim 后 | 2.4 MB | 工作集归还；commit 仍 364MB（pymalloc arena 保留） |

- F1：峰值在**构建末期**（子串大 dict 未释放 + 压实临时结构叠加），
  不是新旧索引共存（后者已被 v2.20.0 release_first 治掉）。
- F2：峰值只出现在 on_load 启动与滑窗变更重建两条路径；同步是增量合并，无峰值。
- F3：宿主耗时约束（MaiBot v1.4.5 源码核实）：`runner_spawn_timeout_sec`
  默认 **30s**（official_configs.py:5883），runner.ready 在所有插件 on_load
  完成后才上报（runner_main.py:544）——与同 Runner 其他插件共享；
  超时是**软阈值**：插件标记 timed_out 但「仍在后台加载，Runner 未被停止」
  （supervisor.py:424），on_load 无独立超时、不会被杀。
- F4：子串桶有 `_SUBSPAN_MAX_SONGS=3` 准入上限（plugin.py:596），
  **哪 3 首歌入选取决于插入顺序**——任何改变遍历顺序的重构都会改变
  入选集合，违反行为零变化。保序方案只有「两遍重读源（同序）」或
  「带全局序号的事件流 + 稳定排序」。
- F5：trim 后 commit 仍 364MB（pymalloc arena 不归还）——与本次峰值问题
  同源但属另一课题，本次不处理，记录备查。

## 候选路线（待原型数据裁决）

- **A2 两遍重读源**：第一遍只建整句表→压实释放；第二遍重读关键词文件/DB
  只建子串表（同一代码路径同一顺序，语义天然等价）。预估峰值 ~370-400MB，
  耗时 ~30s（子串插入做两次）。
- **B-lite 事件流**：构建时子串事件记成带全局序号的定长记录（~50MB array），
  按 gram 稳定排序后分组取前 3（序号保序）。预估峰值 ~200MB 量级、
  耗时与当前相当；难点是 150 万键的排序实现。
- **C 分块压实边压边删**：dict 骨架不收缩，收益有限（~450MB），基本出局。

## 原型实测（2026-11-18，工作区 proto_peak.py，真实素材 + 36MB 同步库）

同进程各自 trim 后起跑，峰值为进程级 PeakWorkingSetSize：

| 路线 | 峰值 RSS | 耗时 | 等价性 |
|---|---:|---:|---|
| 生产 v2.20.0（参照） | ~500 MB | ~18-26s（波动） | — |
| A2 两遍重读 | **468 MB** | 27.7s | 两表 0 差异；lyrics 差异是原型裁剪口径简化（user_keys 传空集），非路线缺陷 |
| B-lite v1（buckets dict 分组） | 666 MB | 24.1s | 全等价，但分组阶段 150 万条目 dict 反而更差 → 弃 |
| **B-lite v2（流式分组+array 边界）** | **402 MB** | 26.6s | **两表 175 万键全量 0 差异 + lyrics 222 首等价** |

B-lite v2 阶段分解：事件流 1,739,277 条（20MB array）+ grams 注册表；
两遍稳定排序 0.8s（先 seq 后 gid，Python sorted 稳定性保证 (gid,seq) 序）；
流式分组 1.5s（扁平 vals + array 桶边界，无大 dict）；键排序+组装 8.1s。

关键认知修正：
- **A2 收益甚微**（500→468）：峰值大头是子串 dict 254MB 本体 + 压实临时，
  错峰只省掉整句 dict 的 ~47MB 叠加，且耗时 +50%。不值得。
- **B-lite 的 grams 注册表（gram->gid dict + str，~150MB）是新的常驻代价**，
  但换掉了子串 dict 的桶列表/歌名引用/压实临时叠加，净峰值 500→402（-20%）。
- B-lite 排序出乎意料地快（0.8s）：两遍稳定排序 list[int] 远比元组 key 省内存；
  耗时大头在键 UTF-8 编码+排序+组装（8.1s），与生产压实阶段（~10s）同量级。
- 生产构建耗时本机波动大（18~26s，HDD/缓存影响），B-lite 26.6s 与生产上界相当，
  不构成显著回归；宿主 30s 软阈值（F3）两者都贴边，属既有状态非本次引入。

## 终选与生产实现（2026-11-18，用户「开工」授权）

路线终选 **B-lite v2（事件流）**，落地为 `subspan_events.py` + plugin.py
正式构建路径（原型 monkeypatch 改写为生产代码）。生产实现与原型有一处
关键差异：原型用「两遍稳定排序 list[int]」，生产改用**计数排序散射**
（全程 array，段内天然事件序升序，无需排序）+ 分块键输出，峰值更稳。

|---|---:|---:|
| 构建峰值 RSS（分阶段 _peakphase） | ~500 MB | **412.5 MB** |
| 构建峰值 RSS（完整路径 measure_mem3） | ~500 MB | **414.2 MB** |
| 构建后稳态 RSS | ~4 MB | 4.9 MB |

峰值低于 v2.19.0 基线 429MB，达成 P1 目标；稳态/存活/延迟与 v2.20.0 持平。

### 开发期关键教训：分块键输出必须沿全局字节序切

生产首版按 **gid 区间**分块（每块 65,536 个 gid）、只在块内排序，块间按
gid 序拼接。gid 是「首次出现序」，与 gram 字节序无关 → keys blob 整体乱序
→ CompactIndex 二分失效：**键明明在 blob 里（`blob.find` 命中、桶数据正确），
`_find` 却返回 -1、`get()=None`**。真实素材子串键从 150 万掉到 30 万、
「可是我并不喜欢吃鱼～～」端到端 FAIL。

小规模单测全过是因为 gram 数 < 65,536 只有一块；原 `test_chunk_boundary`
用 `f"{i:05d}尾"` 恰好字节序==gid 序，掩盖了缺陷。

修复：先对全部 gid 做一次**全局字节序排序**（`sorted(range(num_grams),
key=gram_list.__getitem__)`，str 码点序==UTF-8 字节序，与 from_mapping 的
`sorted(mapping)` 同口径），排完转 `array('I')` 再沿该全序分块——块间天然
有序，且块内无需再排序。此时事件 array 与注册表 dict 已释放，排序临时
（list[int] ~12MB）叠加可控，峰值未回退（412.5MB）。

防回归：① `assert_equiv` 增加 keys blob 全局字节序非降的**结构不变量检查**
（不依赖 get() 碰巧命中）；② 新增 `test_chunk_global_byte_order`：确定性
伪随机打乱插入序，强制 gram 字节序与 gid 序背离且跨多块（70,000 gram）。
