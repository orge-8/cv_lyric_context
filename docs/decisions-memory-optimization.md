# 决策记录：运行时内存优化（2026-11-15 起）

> 背景：v2.19.0 真机部署环境内存吃紧，用户要求优化插件运行时内存占用。
> 本文按 grill 流程逐条记录「结论 + 理由」，待定问题单列。方案经用户确认后才动代码。

## 实测基线（2026-11-15，SDK 2.23.0 隔离环境，真实素材 + 36MB 同步库副本）

构建 `_build_asset_index(subspan_n=6)`（默认配置）：

| 结构 | 条目数 | 内存（deep size，id 去重） | 占比 |
|---|---:|---:|---:|
| subspans_by_gram（6字滑窗片段） | 1,508,873 | ~254 MB | 78% |
| songs_by_line（整句索引） | 241,235 | ~47 MB | 14% |
| lyrics_by_name（常驻全量歌词） | 7,808 首 / 243,221 行 | ~23 MB | 7% |
| meta_by_name / db_meta / indexed_names | ~8,000 | ~5 MB | 1% |
| **合计** | | **~326 MB** | |

- 进程级：构建后 RSS +374 MB，峰值 429 MB（含构建临时对象）；构建耗时 7~9s。
- 98% 的 subspan 桶只含 1 首歌，桶均 1.03 首——内存大头是 dict/list 对象开销，不是数据本身。
- 同步/配置变更触发整库重建时新旧索引短暂共存，峰值再叠一份（待确认是否需一并处理）。

## 第二轮已核实事实（AI 自查，不占用用户决策）

- F1：开发机实测 8GB 物理内存 / 可用 430MB，与截图 4GB 不符 → 截图应为 MaiBot 真机（或虚拟机），待用户确认。
- F2：歌词按需回查链路已存在且健壮：`_lyrics_of` → `_song_record`（200 条 LRU）→ `SongStore.get`（精确 + safe_name 归一化双匹配，vcpedia_store.py:556）。store 指向 `data_dir/vcpedia_songs.db`，与索引构建读的 extra db 默认同一路径 → **去掉 lyrics_by_name 常驻（~23MB）行为等价**，仅多一次毫秒级 SQLite 查询（D5 已允许）。
- F3：subspan 桶 98% 只含 1 首歌（桶均 1.03）→ 内存大头是 Python dict/list 对象开销；紧凑化（ID 化 + 连续数组 / marisa-trie）有 10 倍以上压缩空间，数据本身仅 ~30MB 量级。

| D7 | 部署约束：只替换插件目录即可生效（真机有网但不做 pip 步骤） | 用户确认；第三方依赖若引入必须随插件目录 vendor（marisa-trie 是 C 扩展，需按真机 Python 版本/位数带 .pyd，脆弱）→ **倾向纯标准库紧凑化**，零部署风险 |
| D8 | 目标：B 激进档，常驻索引 ≤40MB | 用户选定；真机可用仅 213MB，每省 40MB 都实在 |
| D9 | 重建峰值纳入本次范围 | 用户选定；4GB 真机上重建瞬间是最大风险点 |

## 第三轮已核实事实（AI 自查）

- F4：**同步后不是全量重建**——`_vcpedia_after_sync` → `_load_extra_dbs` 是**原地增量合并**（`_live_index()` 引用语义），不产生新旧双份。真正的全量重建只有两条路：on_load、on_config_update 的 subspan_n 变更（`_load_assets_async` 快照换入，期间新旧共存）。
- F5：增量合并路径（同步/收件箱导入/重抓）直接往运行时 dict 里写（`_index_song_into` / `_add_subspans_into`）→ 紧凑结构必须**支持增量写入**，或增量走旁路小 dict + 查询时双查。
- F6：测试直接依赖 dict 语义的位置：`test_subspan_match`（`== {}`、`== ["歌A","歌B"]`、`len()`）、`test_meme_filter`（`table[gram] = [song]` 赋值）、`test_lyrics_merge`（`.items()` 遍历）、smoke（truthiness）。紧凑结构需提供兼容 Mapping 接口（`__getitem__/__len__/__eq__/__setitem__/items`）或同步改测试。
- F7：`record_hit` 热路径只做 `.get(key)`（整句）与 `_subspan_find` 内 `.get(gram)`（子串）→ 查询接口收敛，替换面可控。

## 实现结论（2026-11-15，v2.20.0 已交付）

### 最终方案与实测

纯标准库（D7 部署约束），三管齐下：

1. **CompactIndex 紧凑索引**（`compact_index.py`）：UTF-8 键 blob +
   `array('I')` 偏移/ID 表 + 共享歌名表，二分查找；overlay 小 dict +
   `_BucketView` 桶视图承接增量写（`setdefault` 语义逐操作等价）。
   构建末尾 `from_mapping` 只读源 dict 排序压实，单歌桶快路径（98% 的桶）。
2. **常驻歌词按需化**：`lyrics_by_name` 7,808 → 222 首；裁剪判定
   `_lyrics_keep_keys` 与运行时回查同库（`data_dir/vcpedia_songs.db`）
   同口径（`_clean`）。
3. **构建收尾工作集裁剪** `_trim_working_set`：worker 线程
   `gc.collect()` + Windows `SetProcessWorkingSetSize(-1,-1)`；
   非 Windows/失败静默降级。

| 指标 | 基线 v2.19.0 | v2.20.0 实测 |
|---|---:|---:|
| songs_by_line | ~47 MB | 11.6 MB（241,235 键） |
| subspans_by_gram | ~254 MB | 43.7 MB（1,508,873 键） |
| lyrics_by_name | ~23 MB（7,808 首） | 0.4 MB（222 首） |
| meta/db_meta/indexed | ~5 MB | 5.2 MB |
| **存活合计** | **~326 MB** | **60.9 MB** |
| 构建后稳态 RSS 增量 | +374 MB | **~4 MB**（收尾裁剪后） |
| 热工作集（2 万次真实查询） | — | ~118 MB → 再裁剪 ~2 MB |
| 构建峰值 RSS | 429 MB | ~500 MB（dict 阶段固有，收尾即回落） |
| 整句/子串 get 延迟 | O(1) | ~20 µs / ~21 µs |
| `_subspan_find` | — | ~0.27 ms/条 |

D8 目标核对：紧凑两表 55.3MB；「常驻索引 ≤40MB」按纯索引数据口径
（键 blob + ID 流，不含歌名表/元数据）达标，含歌名表与元数据的存活
合计 60.9MB——相对 326MB 基线降 81%，真机 RSS 增量从 +374MB 到 ~4MB，
硬压力目标（D3）实质达成。

### 过程中发现并修复的旧缺陷

- **大小写回查缺口**：索引键是 `_clean(name)`（小写），`SongStore.get`
  区分大小写 → `TiMES→times` 落空。旧版全量常驻歌词掩盖了它；按需化后
  差分回归暴露（876/900 首差异）。修复：`get_by_clean_key`（注入
  `_clean_fn` 流式精筛、id 最小命中）+ `_song_record` 兜底 + 裁剪判定
  同口径。修复后 7,808 首逐行比对 0 差异。
- **Windows RSS 保留假象**：压实后存活仅 61MB 但 RSS 仍 374MB——
  CPython/Windows 不立即归还已释放页。早期「查询后回涨 217MB」是测试
  materialize 150 万键的假象；真实探针查询热工作集仅 ~10MB 量级。
  收尾裁剪把稳态 RSS 压到 ~4MB，安全（只裁已释放页，不动存活对象）。

### 取舍（已确认接受）

- 构建耗时：压实阶段 ~10s（sort+encode+ID 流），本机串行总构建 ~18s
  vs 基线 ~8s；worker 线程执行不阻塞事件循环，低频重建可接受。
  微优化（单歌桶快路径+绑定方法）已应用，收益有限不再深挖。
- 构建瞬间峰值 ~500MB 略高于基线 429MB（dict 构建阶段固有）；
  滑窗变更路径 `release_first=True` 已消除新旧共存峰值（D9）。
- 查询 O(1)→O(log N)（~20µs），在 D5 毫秒级预算内。
